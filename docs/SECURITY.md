# Security and tested boundaries

Optional subagents inherit the configured portable model, transport and tool-profile ceiling. Child sessions cannot load ambient extensions, skills, context files, external providers or machines. Bundled roles are allowlisted; foreground batches are capped at 8 children and upstream session limits at 32, with no grandchildren. Web tools remain separately opt-in and use isolated web request scope in children as in the parent. Detached runners, scheduling, automatic worktrees and workflow scripts are disabled. Extension artifacts and child transcripts remain under the selected state directory and can contain source/tool output; `--no-session` is not an artifact suppression guarantee. See SUBAGENTS.md. These controls do not sandbox native code or protect a credential deliberately included in prompts/tool output.

Credentials default to process memory/environment and the child's environment. A hidden terminal prompt avoids shell history. They are not embedded in arguments, the public executable, generated models.json, or normal transcripts. A fresh agent directory for each launch prevents reuse of host auth/settings and launcher-saved secrets. Pi's interactive login can still write auth material into that launch directory; normal shutdown attempts to remove it. Crashes, forced termination, malware, debugging tools, dumps, privileged inspection, and user prompts or shell commands containing secrets remain outside that guarantee. Inherited environment variables, including endpoint/proxy secrets, can be inspected by child processes. Do not regard tool profiles as secret isolation.

Only use trusted configuration and state directories. The launcher rejects junctions/symlinks on its own executable-runtime/state/config paths, validates archive containment, hashes every cached payload file before execution, rejects unexpected cached files, serializes extraction, and stages complete runtime directories. It does not defend against concurrent malicious writes by another process with the same filesystem permissions between verification and execution. Writable project files and transcripts are untrusted input to the model.

The model fetch guard allows only POST to the configured origin plus `/chat/completions` or `/responses`. It rejects redirects, alternate origins/ports/protocols, model discovery URLs and extra query parameters. Azure's configured version query is added after validation. It removes inherited provider Authorization headers, then adds the selected session credentials. Additional CA bundles preserve validation. Extension policy initialization errors terminate the process before a model request. Pi's offline startup suppresses catalog/version/telemetry work before the extension is loaded.

With `--web` or `web.enabled: true`, only `web_search`/`fetch_content` execution receives a separate asynchronous web-request scope. Model calls and concurrent unrelated requests retain the model guard. Web requests do not get model authorization or configured model headers. Exa/Brave headers are retained only for their respective search API routes (or explicitly configured mirrors). Page reads default to HTTPS and may be restricted with exact `web.allowedOrigins`; redirects are revalidated. Provider redirects are rejected. Jina fallback is independently off by default; enabling it shares requested page URLs with Jina. The web guard does not provide a DNS/private-address sandbox: with no content allowlist, it permits HTTPS page reads including reachable internal hosts other than the configured model origin. Use a content allowlist and enterprise network controls when separation matters. Details in WEB_ACCESS.md.

These are application controls. Full-profile PowerShell and user-entered commands can access files, start processes and use the network with the user's privileges. Pi's built-in interactive actions, native HTTP/socket clients and any future upstream code paths that do not use global fetch are outside the model transport guard. An explicitly configured public endpoint is allowed. Use enterprise network egress restrictions for a strict no-public-network environment. The product does not change firewall, execution, proxy or trust-store policy.

Tests contact synthetic loopback HTTP/HTTPS and CONNECT proxy servers only. They assert exact paths/auth/tool declarations, file results, profile enforcement on continuation, relocation, no key bytes in persistent test state, TLS trust failure despite an inherited insecure environment flag, redirect non-delivery, and no fallback provider. Guard unit tests assert zero transport calls for attempted public/unconfigured origins. This is not a packet-capture audit or proof about every upstream interactive feature. Tests do not call a real Azure tenant, production Ollama deployment, corporate proxy or paid provider.

Report vulnerabilities privately to the repository owner; do not attach real keys, internal URLs, code or session transcripts to public issues. Releases should be built from clean committed source and have their signature/hash manifest verified.
